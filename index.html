CS-01 · Security operations · Vendor strategyDelivered

MSP exit and endpoint migration automation

I moved the company from an MSP-owned security and management model to tooling the company owns, in under 60 days, with no production impact. To get there I wrote an unattended migration that swapped management agents on every endpoint without dropping EDR protection.

Problem

The MSP owned the RMM, EDR, and backup tenants. That meant limited visibility, persistent third-party access, and cost that grew with headcount. After the IT director left, the company needed control of its own environment without adding staff.

What I owned

  • Built the business case: vendor comparison workbooks, topology diagrams, and implementation Gantt charts comparing three models (incumbent MSP, an alternative MSP, and company-owned ConnectWise + Arctic Wolf).
  • Ran negotiations and timed the contracts to lock pricing ahead of a vendor rate increase. Contracts were executed through the CFO.
  • Restructured the incumbent MSP to a break-glass SOW, used for escalation only. Removing its standing access was part of the security decision.
  • Reported bi-weekly red/yellow/green status to the CFO across every workstream.

Engineering

  • Unattended migration script: stages installers before removing anything, verifies SHA-256 hashes, removes the legacy agents, installs the new RMM and remote-support clients, then resumes itself after reboot through a scheduled task that deletes itself when finished.
  • Guardrails: SentinelOne is never touched, and the script verifies that exactly one remote-support client is left.
  • Validated on sandbox machines before fleet rollout. Afterwards, built RMM first-check-in packages so new and remote devices get the MDR agent and Sysmon automatically. Installers are hosted in the RMM so laptops off the network still receive them.

Result

The company now owns its RMM/PSA, EDR, MDR, DNS filtering, email security, and backup. Arctic Wolf provides 24/7 MDR. Cost is about $40K a year lower than the MSP-owned option, and the gap grows with headcount. Production saw no disruption. The incumbent MSP no longer has any presence in the company's management tenant.

What I'd keep

Stage and verify everything before removing anything. Make every step resumable, and never let the migration touch the security agent.

CS-02 · Email security · Change managementDelivered

Email security cutover to Proofpoint

I planned and ran the inbound mail cutover from Microsoft 365 native filtering to Proofpoint, including domain authentication, URL defense, quarantine, and phishing-simulation delivery. A rollback was ready at every step.

Problem

Email is the company's main attack surface, and the previous setup left filtering and awareness testing in other hands. Partway through the MSP transition I re-evaluated the planned awareness platform. Cost modeling showed Proofpoint covered filtering and training for less money.

Engineering

  • MX cutover and Microsoft 365 inbound connectors restricted to Proofpoint, so mail can't bypass the filter.
  • SPF, DKIM, and DMARC aligned across sending services. URL defense and quarantine policy configured with user digests.
  • Advanced Delivery settings so phishing simulations reach inboxes without weakening real filtering.
  • Captured the prior configuration before cutover so rollback was a documented, timed procedure.
  • Now integrating Proofpoint with the MDR provider's active-response tooling.

Result

Production inbound mail through Proofpoint was validated after cutover. The company owns its filtering and awareness program, and annual spend is lower than the platform originally planned.

CS-03 · Architecture · Capital planningDesign & procurement complete · migration underway

Virtualization and storage refresh

The SAN was end-of-life, the hosts were aging, and the domain controllers ran Server 2012. I designed the replacement, ran the licensing and options analysis, and drove procurement. I'm now leading the migration.

Constraints

  • Production and ERP-adjacent workloads can't take long outages, so the cutover has to fit the midnight–4 AM window.
  • Windows Server licensing is per core and depends on VM count. Getting it wrong is expensive either way.
  • The platform has to be supportable by a small team, with vendor support behind it.

Decisions

  • Two Hyper-V hosts on Windows Server 2025, 32 physical cores each, sized for the current ~11 VMs plus failover headroom.
  • Lenovo shared storage replacing the end-of-life SAN, with redundant NICs and power.
  • Licensing modeled before purchase: Standard vs. Datacenter virtualization rights against VM placement, plus CALs.
  • Proxmox evaluated against Hyper-V before committing to the platform.
  • Domain controllers will be rebuilt on 2025 rather than hardened in place. I deferred Sysmon on the 2012 DCs to avoid adding risk to systems that are being retired.

Status

Hardware is purchased and in fulfillment. Migration sequencing, rollback, and acceptance criteria are defined. I'll add host cutover and SAN retirement dates when production acceptance is complete.

Backup and recovery modernization

I brought server backup in-house with Axcient direct-to-cloud protection, scheduled around production. I'm now adding a local recovery appliance on an isolated network so restores don't depend on internet bandwidth.

Problem

Backups were provider-managed, and some jobs ran into production hours, which hurt reliability. The company needed its own recovery capability, plus a fast local restore path for a plant that can't wait on a cloud download.

Engineering

  • Axcient x360Recover direct-to-cloud on all servers, live September 2026. Schedules are staggered into non-production hours so jobs don't compete with the lines.
  • Traced recurring failures to VSS errors and to the EDR quarantining backup components. Resolved them with the security and backup vendors without weakening EDR policy.
  • Built a bring-your-own-device BDR appliance on company-supplied server hardware instead of buying a commercial appliance. Racked, initialized, and placed on a dedicated backup VLAN.

Next evidence

Next steps are a documented restore test with measured restore time and achieved RPO/RTO per workload. I'll publish those numbers here when they're measured, not before.

CS-05 · Application integration · ManufacturingBuilt · production acceptance pending

On-prem production labeling integration

Product labels print from a cloud service. The ERP vendor's connector only speaks to that cloud service, so I built an on-prem BarTender environment and my own middleware to give the plant a labeling path that doesn't depend on the cloud.

Problem

The plant produces about five million egg rolls a week, and every case needs a label. A cloud labeling outage stops shipping. The ERP vendor's connector sends a payload built only for the cloud product, and no vendor offered an on-prem path.

Engineering

  • Stood up an on-prem BarTender server.
  • Wrote a middleware adapter that accepts the ERP's JSON print requests and translates them into jobs the on-prem BarTender can run.
  • Published the API through IIS Application Request Routing and URL Rewrite with HTTPS and authentication, and configured the firewall to allow it.
  • Validated API reachability (Swagger) from inside and outside the network.

Status

The server, proxy, and adapter are built and reachable. End-to-end production failover testing and vendor acceptance are the remaining steps. I'm not presenting this as a finished replacement until those pass.
